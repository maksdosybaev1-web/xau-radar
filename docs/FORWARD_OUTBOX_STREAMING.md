# Последовательное восстановление уведомлений SBR/RBS

Дата: 27 сентября 2026.

При старте SBR/RBS ранее помещали все записи с `delivery_alert` в словарь `pending_delivery`, включая уже обработанные уведомления. Теперь `ReplayPending` хранит путь, размер журнала на момент создания и позицию чтения. При первом восстановлении журнал читается по одной записи. В словаре остаются только новые события текущего процесса, ожидающие передачи в локальную очередь.

Позиция продвигается после успешного `AlertStore.add`. Если вставка завершилась ошибкой, следующий вызов повторяет ту же запись. При перезапуске чтение начинается заново; защита по идентификатору в AlertStore сохраняет статус ранее обработанных уведомлений. Проверки давности и разрешения доставки остаются прежними. Само восстановление не отправляет сообщения в Telegram.

Изменение подключено к SBR/RBS. FVG пока использует прежний словарь; общая функция восстановления также перестала создавать дополнительный список из всех элементов словаря.

Проверка: `python -m unittest discover -s tests -q` — 158 тестов прошли. Новый тест обрабатывает 1 000 записей, вызывает ошибку на восьмой, затем проверяет продолжение без пропусков, порядок записей, сохранение признака разрешения доставки и обработку нового события. Отдельно проверено явное прекращение восстановления при усечении журнала. Прежние тесты проверяют отсутствие повторной доставки после перезапуска и отсечение старых событий.

Границы: чтение большого журнала всё ещё занимает время и выполняется синхронно. Размер одной записи не ограничен; поддерживается один писатель. Курсор не сохраняется между запусками — повторное чтение опирается на идемпотентную вставку в AlertStore. Это ограничение памяти восстановления SBR/RBS, не всего радара.

Радар, MT5-мост и Telegram не запускались; тестовые данные создавались во временных каталогах.
