# Индекс дубликатов SBR/RBS на диске

Дата: 27 сентября 2026.

В живых обёртках SBR и RBS множество `seen` заменено на `JournalKeys`: поиск ключа, добавление и подсчёт выполняются в SQLite. Рядом с каждым JSONL создаётся файл с суффиксом `.jsonl.keys.sqlite3`. Полный набор ключей больше не загружается в Python-множество.

JSONL остаётся источником истины. При создании обёртки индекс перестраивается в транзакции с последовательным чтением журнала. Повторяющиеся ключи объединяются, записи старого индекса, которых нет в журнале, удаляются. Отсутствующий индекс создаётся заново. Повреждение SQLite не скрывается: ошибка останавливает создание обёртки; автоматическое удаление повреждённой базы не реализовано.

При новом событии сначала выполняется запись JSONL с `flush()` и `fsync()`, затем обновление индекса. После сбоя между этими действиями повторный запуск восстановит ключ из журнала. Работа нескольких писателей с одним журналом не поддерживается. Соединения SQLite закрываются после каждой операции.

Проверка: `python -m unittest discover -s tests -q` — 156 тестов прошли. Дополнительно проверены 1 000 записей с 500 уникальными ключами, отсутствующие и лишние ключи индекса, восстановление удалённого индекса, сбой обновления индекса после сохранения события и отсутствие повторной записи после перезапуска в обоих режимах. Сравнение событий с исходными моделями остаётся в наборе тестов.

Ограничения: это перенос ключей из памяти на диск, а не ограничение размера дискового журнала. При старте журнал читается дважды последовательно: для индекса и для буфера последних событий/восстановления очереди. `COUNT(*)` обращается к SQLite при запросе общего количества; скорость на многолетнем журнале отдельно не измерялась. Очередь восстановления уведомлений и другие подсистемы требуют отдельной оценки памяти.

Радар, MT5-мост и Telegram не запускались; реальные журналы этим этапом не перестраивались — тесты работали во временных каталогах.
