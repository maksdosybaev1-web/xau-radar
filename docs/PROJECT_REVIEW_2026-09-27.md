# Анализ текущего проекта — 27 сентября 2026

## Вывод

Проект уже содержит несколько отдельных исследовательских моделей и работающую интеграцию чтения MT5. Он пригоден для дальнейшего исследования, но непрерывное наблюдение и доставка уведомлений ещё ненадёжны. Торговое преимущество не подтверждено. Главная ближайшая задача — исправить жизненный цикл служб и целостность записи событий, затем продолжать измерения.

Проверены текущие исходники, сохранённые результаты, документация, API состояния и журнал ошибок. Выполнены 82 существующих теста: все прошли. Два дополнительных изолированных воспроизведения выявили проблемы, не покрытые текущим набором. Они не отправляют сообщения и используют временную базу. Торговой код, конфигурации и работающие процессы в рамках анализа не изменялись.

## Приоритетные находки

### 1. Высокий приоритет: поток Telegram действительно завершился

`app/notifications.py:166–167`, `app/operations.py:12`.

В `runtime/bridge-error.log` есть traceback: `PermissionError [WinError 5]` при замене `delivery-status.json`. Обработчик ошибки пытается записать heartbeat ещё раз; вторая ошибка выходит из обработчика и завершает поток. Автоматического восстановления потока нет. Во время анализа API показывал `worker_alive: false`, «Очередь не отвечает», при работающем MT5-мосте. Это наблюдаемый сбой, а не гипотеза.

Первопричина отказа Windows в замене файла не установлена; нельзя без отдельной проверки приписывать её конкретному процессу. Проблема кода — возможность гибели доставки из-за записи диагностического статуса. Нужны независимая обработка ошибки heartbeat, ограниченные повторы записи и контроль жизни worker. Тест должен моделировать ошибку и в основном пути, и внутри обработки ошибки.

### 2. Высокий приоритет: событие может остаться без уведомления после сбоя SQLite

`app/snr_sbr_live.py:43–55`; аналогичная последовательность в `app/snr_rbs_live.py:49–62`.

Сначала событие пишется в JSONL и добавляется в `seen`, затем помещается в SQLite-очередь. Если второй шаг падает, повторное событие подавляется как уже обработанное. После перезапуска `seen` восстанавливается из JSONL, но недостающая запись очереди не восстанавливается.

Изолированное воспроизведение SBR: искусственный `sqlite3.OperationalError` при `alerts.add`; затем повтор той же записи после устранения ошибки. Итог — 1 событие в журнале, 0 уведомлений в очереди. У RBS тот же порядок операций, но отдельное воспроизведение для него не выполнялось.

Нужна транзакционная запись события и задания доставки в одной базе либо сверка журнала с очередью при восстановлении. Повтор должен сохранять исходный ID и ограничение срока доставки.

### 3. Средний приоритет: Classic может засчитать возврат после срока уровня

`app/snr_classic.py:61–80`, `app/snr_classic.py:89–92`.

Касание проверяется на каждой M1 раньше проверки возраста на закрытии M5. Уровень остаётся `armed` за границей 24 M5 и может получить `touch_observed`, прежде чем код дойдёт до `expired`.

Изолированный пример: срок уровня 899700, касание стало известно в 899820, результат `touch_observed` — на 120 секунд позже срока. Тесты существующей проверки истечения вызывают `on_m5` напрямую и не покрывают порядок обработки M1. Нужна явная проверка срока до касания и пересчёт Classic после исправления. Масштаб влияния на сохранённые 822 наблюдения пока не измерен.

### 4. Средний приоритет: FVG-симуляция не продолжается после перезапуска

`app/mt5_bridge.py:30–33,81`.

`begin_forward` очищает сделки, позиции и кривую, возвращает начальный условный капитал. Журнал событий не является снимком состояния портфеля. Поэтому несколько запусков нельзя объединять как непрерывный демопрогон. Нужно сохранять состояние либо явно разделять сеансы и не выдавать их сводку за единый портфель. Это известное ограничение, по-прежнему присутствующее в текущем коде.

SBR/RBS при запуске заново рассчитывают состояние по истории и восстанавливают набор ID; их режим сейчас `live_signal_only`. Это восстановление наблюдателя, а не портфеля с открытыми сделками.

### 5. Средний приоритет для длительной работы: накопление памяти и стоимости обновления

SBR/RBS сохраняют все терминальные уровни и события в памяти; `step` проходит по всем уровням каждую минуту. `SBRForward.state` каждый цикл читает весь JSONL, чтобы оставить последние 50 строк. При длительном запуске объём работы растёт вместе с историей. Аварии из-за этого не наблюдалось; это вывод по коду, без нагрузочного измерения.

Нужны отдельный набор активных уровней, постоянное хранение завершённых записей, чтение последних записей с индексом и ограниченный буфер интерфейса. В Classic уже есть отдельный `active`, который можно использовать как образец организации.

### 6. Документация местами противоречит текущей реализации

В начале `PLAN_AUDIT.md` указано 72 теста и утверждается, что RBS ещё не подключён к MT5/Telegram. Сейчас `mt5_bridge.py` создаёт `RBSForward`, а его код ставит уведомления в очередь; тестов уже 82. Старые отчёты также сообщают о здоровой очереди, тогда как текущий поток завершился.

Исторические записи стоит сохранить как историю, но нужна одна актуальная таблица: «реализовано / подключено / проверено на свежем потоке / оценено». Наличие кода не подтверждает доставку живого сигнала или прибыльность.

## Что уже сделано хорошо

- MT5-интеграция читающая; расчёты и симуляция отделены от исполнения брокерских заявок.
- Есть закрытые свечи, отложенное подтверждение экстремумов, тесты причинности, учёт bid/ask и расходов в исторических опытах.
- Разделены FVG, индикаторный WATCH, SBR, RBS и Classic. Связь с материалами и исследовательские допущения документированы.
- Telegram хранит токен через DPAPI. Захват задания в очереди атомарный; сетевой запрос не держит соединение с журналом. Это полезная защита, но она не устраняет разрыв между JSONL и очередью из пункта 2.
- Добавлен `TickArchive`: сбор истории bid/ask через `copy_ticks_range` и запись окон запросов. Код прямо различает покрытие запросами и доказанную полноту тиков.
- ИИ используется для пояснений; сравнение фильтра явно помечено как ограниченное исследование фиксированных сигналов.

1. Устранить гибель Telegram-worker, затем проверить автоматическое восстановление без отправки выдуманных рыночных сигналов.

5. Проверить свежие котировки и архив тиков, затем считать исходы по отдельным версиям сценариев.
6. Возвращаться к новым моделям и ИИ-фильтрам после стабилизации измерения.
